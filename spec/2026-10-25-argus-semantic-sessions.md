## 1. 背景与目标

2026-10-22 实测暴露的是上下文表达、结果预算和工作交接的问题，不能把全部现象解释为模型能力不足。当前源码已经具有工具预算、原始结果落盘、会话历史压缩、同聊天执行互斥及报告重试；本轮复用这些设施，修复缺口，不再建设一套同义系统。

用户确认：session 按语义上下文归属。新的相关消息即使到达时 Agent 仍在工作、或原语境已闲置超过五分钟，也可以归入原 session。但“归入 session”不等于“立即将正文插入当前任务”。新消息先进入插件可读取的持久工作集合，运行中只提供简短提醒，正文由 Agent 自主读取。

这个要求需要 Argus 的筛选/归属、Agent 的会话/插件和 Gateway 的可信控制边界一起变化，不能拆成互不相关的应用本地需求。

## 3. 已确认的行为边界

### 3.1 给模型的信息

消息内容必须高密度表达：谁、在何处、何时说了什么；为什么关注这一批消息；需要 Agent 判断或处理什么。必要的身份信息、聊天场景和回复关系不能因“精简字段”而被删除。

示例仅说明表达目标，不规定逐字模板：

> 10:32，QQ 开发测试群的 OakChaser 接着此前的部署问题说：“改过配置，还是超时。”
> 关注原因：正在处理问题的新反馈。结合已有工作判断是否需要继续排查或回复；无需行动也可以。

UUID、binding、游标、重复 locator、内部修订和传输包装留在代码侧。必要的短引用只是证据读取句柄，不成为一份新的存储字段清单。用户没有要求隐藏平台身份；真实操作所需的账号/聊天目标应以简短、明确的形式可用，不能删掉后迫使 Agent 再次查找。

JEV 只筛选“值得 Agent 看”，不判定必须回复。Agent 提供证据和 `handled/no_action` 判断；引用转换、报告组装、去重和重试由代码负责。不把概率分布或机械阈值分类任务转交主 Agent。

### 3.2 语义归属与执行顺序

- Argus 暂用现有 JEV 客户端，在同一聊天及权限范围内选择已有语义 session 或新语境；未来可替换筛选方式。
- 候选使用简短语境和必要近期证据；明确回复关系作为证据，单纯同群、同发送者或最近五分钟都不能证明同语境。
- 明确同语境：关联原 session。明确新语境：安排新 session。无法确认：不强行混入旧 session。
- 同群允许多个语义 session，但本轮同群实际执行仍串行。不同聊天沿用现有全局执行容量规则。
- 尚未启动的新语境可以先由现有等待交接批次保存；不为排队创建 topic/thread 等新业务实体。首次接纳后补充其真实 session 关联。

### 3.3 运行中新消息：通知与正文分离

1. 原始消息和归属必须先持久化。
2. 插件接收到的是可用性通知，重复通知可合并；通知本身不等于正文送达或业务完成。
3. 当前 LLM 请求及工具执行不被取消、重启或抢占。在下一安全步骤边界，插件只提供“当前语境有新的待读消息，可在合适时读取”的有限提醒。
4. 不自动注入新消息正文，不调用 `session.steer`，不将观测包装为用户纠正。
5. Agent 自己决定何时通过 Argus 工具查看。提醒不要求立即处理，也不代替显式 `no_action` 判断。
6. 通知遇到结束竞态或网络丢失，消息仍保留。当前任务结束后可在同一 session 安排后续任务，不以通知失败改建一个语义 session。
7. 空闲 session 的后续任务属于正常调度，不通过 steer 复活已结束 task。连续通知不自动制造无界 LLM 轮次。

### 3.4 过期、卸载、退出续接与历史保留

| 条件 | 行为 |
|---|---|
| 最后一次相关消息或工作结束后闲置 5 分钟 | 软过期；不再默认视为当前活跃语境，仍可按语义重新激活 |
| 超过五分钟，但仍明确同语境 | 继续原 session；语义连续性优先于软过期 |
| 连续 24 小时无相关活动，且没有运行任务、待处理输入或待同步报告 | 退出自动续接候选，回收运行资源 |
| 自动回收后 | 保留持久化历史，不物理删除，不因后台清理破坏幂等对账 |

相关消息到达、重新激活和工作结束刷新相关活动时间；日志、重复通知和报告重试不刷新语义闲置时间。runtime是否驻留内存与session是否可续接分离。运行任务、尚未实际退出的工具及未完成报告同步不因五分钟或24小时到期而被强行释放。

跨应用待办快照可能滞后于消息归属；若已有可信分配的后续工作恰逢清理而遇到退场标记，代码可在认证pending为正、目标scope/owner一致后做内部临时接纳，保持退场/隐藏直到精确远端绑定证明成立，再原子恢复资格与持久绑定。不得凭调用方revive标记复活任意会话、先远端绑定后才记录本地身份，或将不明确绑定响应当作明确未绑定来释放。

### 3.5 图片、工具结果与动作事实

- 当前在规则侧过滤不可处理的图片类输入，不用 `[image]` 伪装正文；图文混合保留有意义的文字，单独 @ 不代表图片内容已经可读。
- 保留原有图片/类型引用，为以后提供图片位置、资产或图像语义留路径。本轮不接 OCR、视觉输入或不受控远程下载。
- 代码执行/协议成功与业务成功分开。QQ `retcode/status` 的含义属于 snowluma/OneBot 适配，不进入 ReActAgent 或通用 Runtime。
- 仅凭可信结构化业务回执记录成功动作；没有可信回执就标为未确认，不从通用 `success=true` 猜发送成功。动作事实可交给后续 session 上下文，不代表新增发送服务或发送 outbox。
- memory/relationship/knowledge 的查询路线保留。固定开销与动态工具延迟加载由正在开发的功能处理，本轮不另造方案。

## 4. 存储与所有权：不新增数据库表

| 应用/现有表 | 持续职责 |
|---|---|
| Agent `workspaces` | 工作区身份，不改成执行记录 |
| Agent `sessions` | 持续的语义会话、稳定范围、相关活动及当前执行摘要；复用现有 `properties` |
| Agent `session_titles` | 展示标题，不借作 JEV 判断或执行状态存储 |
| Agent `conversation_updates` | 多次交接、报告、动作回执和引用的内部持久记录；内部记录不自动公开或注入模型 |
| Argus `schema_version` | 显式迁移版本 |
| Argus `observed_items` | 原始消息、版本、归属与展示/处理事实；是待读正文的事实来源 |
| Argus `wake_requests` | 每批交接、冻结请求、重试、binding、报告及封口；复用现有 `handoff` |

不新增 execution/session/topic/inbox 表，不跨应用直读或互写数据库，不在 `sessions.properties` 堆积无限增长的历史执行数组。允许修改既有 JSON 的明确键、必要索引及迁移逻辑；无新表不等于保留错误的唯一索引。

session 可以关联多次 wake；一次 wake 的身份/指纹/已确认 binding 仍不可被下一次 wake 覆盖。查询旧 wake、旧报告重试和崩溃恢复必须仍然成立。`scope_key` 继续表示实际执行占用，不代替长期聊天归属。

## 5. 共同控制契约

新路由行为使用显式版本 2；旧版已接纳的执行保留原版本身份和收尾通路，不自动升级指纹或重新运行模型。生产不接受没有版本的猜测请求，不为新增 JSON 键静默放开未知字段校验。v2 的 target_session_id 在首次可能提交前与版本一起冻结并纳入指纹，重试不可用新的路由选择重构旧请求；v1 wire/指纹/解析保留。实际 Agent application HTTP client 和 Gateway envelope 按持久执行/请求版本编码及校验，不取 session 最新版本替代某个旧 binding 的版本。

| 操作 | 共同输入/输出要求 |
|---|---|
| `argus.sessions` | 按可信 scope 查询有限候选；输入 `scope,cursor?,limit`，默认 10、最大 20；返回 `sessions,next_cursor`。候选只有 session 身份、简短语境、相关活动时间和是否仍有工作，不输出完整历史正文或秘密；摘要也按同一内容出口策略过滤 |
| `argus.wake` v2 | 沿用现有冻结消息批次和幂等 wake；增加可空 `target_session_id`。null 表示新语境；非 null 由 Agent 验证同工作区、scope、后台所有权及续接资格；同群繁忙仍排队/退避，不把 status 查询当锁 |
| `argus.notify` | `wake_id,session_id`，无正文、任意指令、URL 或跨 scope 目标；仅将已持久关联的消息可用性传给插件。返回 `protocol_version,accepted,merged`（merged 严格 bool）；成功只表示提醒已接受或合并，不代表正文已读或处理 |
| `argus.status/cancel/release` | 保留既有查询/取消/安全收尾语义；release 是释放本次执行，不是删除语义 session |

所有新增控制操作仍使用专用 `/argus/rpc`、固定服务认证及既有请求大小上限。Gateway 只校验和转发，语义选择归 Argus，候选资格和真实执行占用归 Agent。

原有数据面 bind/deliver/read/history/wait/report/finalize 继续由 Agent 直连 Argus；v2 增加 `available(binding_id)`，只返回 pending_count/watermark，不含正文、不登记送达。另提供受同一服务认证的 session pending 查询：输入 session_id 和 scope，返回 pending_count/last_related_at；包括尚无新 binding 的 waiting 消息。Agent 在自动回收、候选资格和目标续接校验时核对此持久事实，查询失败则保守保留，不把远端不可用当作空闲。v2 deliver 可确认同绑定的初始或已附加消息，正文只有在最终工具结果完整交付后才确认。运行中同语境消息通过持久关联加入当前未封口批次，不改写冻结 payload/指纹；结束后使用新的批次续接同 session。数据面必须区分“同群历史”与“被分配给本语义 session 的工作”，不能读到就认领。

内部 UUID 不变。模型只用插件维护的短引用；同一持久 session 内引用不重新指向另一条消息。旧封口 binding 不重新开放；跨轮历史读取使用当前受认证读取权限重新检查，旧短引用不等于旧 work 授权。

## 6. 共同故障不变量

- 先持久关联再通知；通知是提示，数据库才是事实。重试不重复认领或处理。
- 新消息附加与 finalize 竞争有明确原子边界：已封口则拒绝附加，保留原消息并在同 session 后续调度；不能成功附加后被 finalize 丢失。
- 通知不产生 exposed、不推进正文游标、不生成 handled/no_action，不影响 report cursor。
- 原文因预算截断而未完整交付时，不声称已读；正文游标/短引用映射不得因此跳过消息。v2 初始高密度贡献也必须在最终 ContextReady 视图确认后才登记送达，不沿用提前 deliver；未完整展示的初始项仍能由 wait/read 取回，initial_cursor 不是已读游标。
- 每份报告带其原 wake/binding 归属；复用 session 后不得把旧报告发到新 binding。
- accepted/rejected/unknown 仍分开，未知网络结果不假装拒绝；四个真实停止屏障继续约束执行释放。
- JEV/通知/RPC 故障不绕过权限过滤，也不能从故障推断“当前无任务”。旧 boot 不自动恢复遗留工作；新 boot 只能用新授权批次续接语境，不扩展旧 binding 的代际授权。
- 对曾明确归入语义 session、但重启前未结的旧 boot 消息：仅保留原语义归属，不在启动扫描中自动执行，也不自动标已完成。保护其历史并从自动可执行 pending 计数分开；它不永久阻止资源回收。若当前 boot 收到新的有效相关触发，可将有限旧消息作为 context 提供给新任务，但旧引用不能被新 binding 作为 work 报告，旧状态不因新的回答被批量结清。人工重试/显式接管旧消息不在本轮范围；文档和验收不得把“保留可排查”称为“已自动恢复执行”。

## 7. 非目标

不新增数据库表、嵌套插件、通用消息中台、事件溯源框架、向量话题库、全群并行 Agent、QQ 专用一等工具、绕过预算的 `read_result`、固定冷却代替语义路由、第二套动态工具发现、全局 OneBot 业务判断、物理删除历史或自动部署。显式用户 steer/cancel 的既有功能不被替换成 inbox。

工具预算配置、MCP 返回归一化及空记忆只在 Agent 所有的独立计划中规定；这些不需要制造跨应用协议。

## 9. 依赖顺序与验收

1. Agent 本地结果质量修复可以独立实施；无真实外部调用。
2. 先对齐 v2 最小 JSON fixture、无新表存储和 v1 对账迁移，再接 Gateway 可信边界。
3. Argus 实现规则过滤、JEV 候选归属、等待批次及同语境附加；Agent 插件实现仅提醒/主动读取和跨轮绑定。
4. 完成 5 分钟/24 小时生命周期、历史与报告恢复，最后做三应用离线贯通。

验收至少覆盖：

- A 正在工具调用时出现相关消息：原调用完整结束；模型仅收到短提醒；主动读取之前没有新正文。
- 同群话题 A/B 分 session，B 排队不混入 A；不同群保留原容量行为。
- 6 分钟后同语境仍续接；24 小时内的软过期候选可重激活；正在工作/待同步的更老 session 不被删。
- 重复通知、通知丢失、结束竞态、同 session 第二批报告、跨进程恢复都不丢待办、不串 binding、不重新发送外部动作。
- 图片-only 被规则过滤，图文混合文字保留；提示包含谁/何处/何时/内容/关注原因和工作要求，不包含协议 ID 清单。
- 迁移前后业务表集合完全相同，历史和原有幂等记录保留；普通 session.steer/cancel 与后台隔离不回归。

## 10. 风险、回滚与授权

2026-10-25 用户通过 `/goal` 授权：先由子 Agent 核对需求/方案与源码，再修正冲突、开发并自行完成相关测试，真实端到端由用户验收。授权包含本地代码和隔离测试，不包含修改本机 settings、正式数据库迁移、现有服务重启、真实模型/QQ/MCP、branch/commit/push。开发前已有暂存文档和配置改动保持不动。

两端升级前需备份既有数据，并确认旧执行处于可核对状态。未完成 outbox、旧 binding 和停止证据保留到明确收尾；混合版本不得把未知请求当已处理。回滚只停止新 v2 入站，保留旧任务 status/cancel/report/finalize 通路；不清库、不自动降 schema、不把未读消息批量记 no_action。

执行采用当前分支上的子 Agent 分批实现及逐批审阅，保留无提交差异快照和测试证据。任何实现发现无法在现有表中可靠表达的必要关系，先调整字段/记录与索引方案并说明代价，不能自行恢复“新增 execution 表”的旧建议。

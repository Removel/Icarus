# 知识图谱产品方案：从关系展示到证据地图

2026-09-29。本文是 WebUI 的产品设计方案，覆盖知识库中的知识页面、原始资料及其关系。记忆页继续按自身的身份、范围与生命周期浏览；跨应用的记忆—知识关系留待有明确身份映射与权限规则后再设计。

## 1. 产品判断

用户不会为了看见一张网而打开图谱。图谱应帮助用户完成三件事：**找到与当前问题有关的知识，判断它依据什么，在资料变化时知道哪些内容要复核**。首页不应以全库节点连线画布作为默认入口。全库地图可以作为辅助总览，但主要体验是从搜索结果、知识页面或资料进入一个有边界的局部关系视图。

建议对用户使用“知识关联”或“证据地图”的名称；“图谱”保留为内部技术名称。页面的核心对象是可阅读的内容与可解释的关系，而不是圆点和连线。每条可点击关系都应回答“为什么相连”，且让用户到达两端的原始内容。

产品承诺分三级，避免把演示推导说成事实：

| 层级 | 含义 | 页面表达 |
| --- | --- | --- |
| 明确关系 | 页面正文中的 `[[wikilink]]`，或页面元数据声明的来源 | “引用此知识”“来源资料”；显示方向和原始对象 |
| 派生线索 | 两篇页面声明了同一份来源 | “共同来源”；列出共同来源名称，不表述为语义相似或支持同一结论 |
| 待核查建议 | 将来由检索或模型提出的相似、冲突、缺失等 | 必须有独立的“待核查”状态和证据，未经确认不进入明确关系 |

### 记忆侧的定位

实验页还把“用户 → 分类 → 记忆”画成关系舞台。这里的用户、范围、分类是记录的归属和筛选条件，不是记忆之间的知识关系；把层级筛选画成图容易让用户以为系统发现了联系。正式版建议将记忆做成**按身份与范围约束的可检索记录库**：先选用户、Agent 和工作区，再看生效状态、分类、原文、有效期及修改历史；从 Agent 使用场景进入时，优先回答“命中了哪条记忆、属于谁、在什么范围生效、是否仍有效”。没有检索命中依据的接口时，不能展示“Agent 因这条记忆做了某决定”的因果说明。

记忆页可以复用知识页的搜索、详情、返回和状态样式，但不共享知识图的边模型。未来若明确需要“某条记忆引用某篇知识”，应有双方稳定 ID、用户与工作区授权、建立关系的来源及删除或过期后的处理规则，再把它画成跨应用边；文本相似或分类相同不足以建立这条边。

## 2. 用户与关键任务

主要用户是使用 Agent 和知识库完成工作的操作者，其次是维护导入、编译和修正内容的知识库管理员。同一个人可能承担两种角色，但阅读与维护入口要清楚分开。

| 任务 | 进入位置 | 用户要得到的结果 | 成功标准 |
| --- | --- | --- | --- |
| “这个说法从哪来？” | 搜索结果、知识详情、将来的对话引用 | 看到知识页面、声明来源、可读原文及关系依据 | 从一个结论到可读资料不超过两次选择；无法精确定位时如实告知 |
| “还有哪些内容讨论这个点？” | 知识详情 | 看到显式引用、被引用及共同来源的近邻 | 能区分引用方向和共同来源，选择后可返回原位置 |
| “移除或更新这份资料会影响什么？” | 资料详情 | 看到直接引用它的页面和已有的移除预览 | 影响数与预览对象一致；执行前仍由正式管理流程确认 |
| “哪些内容需要我处理？” | 知识库概览 | 定位失效来源、无来源声明、编译失败等可确定的问题 | 每项都有原因、对象和下一步；不能把未经验证的疑似冲突当确定错误 |

一个典型流程：用户搜索“Plugin Runtime 为什么不能解释领域事件”，进入“插件运行时”页面；右侧看到它显式链接到哪些知识，左侧看到“插件开发指南.pdf”是声明来源；点击来源阅读可用正文，返回后仍停在原页面。若来源不可用，用户看到“来源声明存在，资料当前不可用”和管理入口，而不是一个能点开却没有内容的假节点。

## 3. 信息结构与页面

### 3.1 默认入口

知识库主导航保留“知识页面”“原始资料”的内容管理能力。第三入口建议改为“知识关联”，进入后先显示**搜索框、近期查看的对象（只在有真实本地状态时显示）和可解释的待处理摘要**。没有近期状态或可靠摘要时，展示“搜索知识或从内容列表打开关系”，不自动指定第一篇页面为推荐内容。

全库总览是次级入口“查看全库结构”。只展示可理解的聚合信息，如页面类型、已声明来源的页面数、显式链接数和独立页面数。数字写明统计口径。数据量大时按类型或主题筛选再进入局部视图；不一次画出所有节点和所有边。

### 3.2 局部关系工作台

桌面上方是知识库选择、全局搜索与当前对象路径；主体分为“关系列表 / 当前内容 / 依据与动作”三块。中心是标题、类型、真实摘要及“阅读全文”。左侧显示来源资料、显式入链和出链；共同来源放在单独的“相关线索”分组，不能混入显式引用。右侧展示当前选中关系的解释：关系类型、方向、原始声明或共同来源名称、对象是否可读，以及跳转或管理动作。

默认只呈现一跳关系。每组先展示有限条目与总数，提供“查看全部”列表；排序优先显示明确关系，然后是派生线索。没有可解释的相关性分数时，组内按稳定标题或原始顺序排列，不标“最相关”。画布连线只帮助识别当前选中项，不承担唯一的信息表达；移动端以分组列表为主。键盘可完成搜索、选择、返回、阅读和关闭。

详情页也放一个紧凑的“关联”区：如“3 个页面引用此知识 · 2 份来源 · 1 个来源不可用”。点击才进入工作台，并带上该对象。资料详情对应显示引用页面和“查看移除影响”；这样用户无需专程进入图谱才能获得价值。

### 3.3 关系卡的最小信息

每张卡显示对象名称、对象类型、关系动词、依据和状态。例如：

> 插件运行时 → 引用 → Agent 分层架构<br>
> 依据：页面正文的知识链接；可阅读

> Agent 分层架构 ↔ 共同来源 ↔ 插件运行时<br>
> 依据：均声明“插件开发指南.pdf”；这不表示两页结论相同

来源状态应区分“没有声明来源”“声明了但未找到资料”“资料存在但正文不可用”。不要将它们统一折成“暂无关联”。同名资料无法唯一匹配时显示“来源待确认”，用户仍可阅读页面，但不可生成指向任意一份资料的确定边。

## 4. 关键交互规则

1. 搜索以文字结果为入口。结果显示标题、类型、摘要和命中位置的可用信息；未接真实检索时明示“当前按文本匹配”。选中结果进入局部关系，并保留搜索条件以便返回。
2. 点击关系卡切换关注点；点击“阅读全文”打开内容。不要在单击节点时同时切换中心又弹阅读窗。路径记录用户主动走过的对象；返回可退一站，也可点路径中的任意站。
3. 点击一条线或关系标签，打开“为什么有关联”的解释。显式链接给出源页面与目标页面，来源关系给出声明的名称及解析结果；共同来源列出交集。当前接口无法给出正文段落锚点时只跳到页面或资料级，绝不伪装成精确引用。
4. 切换知识库后清除旧路径和查询；直接打开深链接时，以知识库和页面 `path` 或资料 `hash` 恢复关注点。对象已删除时显示失效状态及返回入口。浏览器前进、刷新与分享链接在正式版应保持一致。
5. 从资料发起“查看影响”时，把直接引用它的页面交给现有移除预览流程；预览结果才是执行前的最终依据。图谱本身不提供一键删除或自动修复。
6. 对空库、无近邻、部分来源失效、加载失败、权限失败分别给出不同状态与恢复动作。失败时保留当前内容和导航位置，避免看起来像“没有关系”。

## 5. 真实数据与可信度边界

当前实现核对结果：

| 数据 / 能力 | 仓库现状 | 产品使用方式 |
| --- | --- | --- |
| 页面显式链接 | OpenKB `POST /api/v1/graph` 返回页面节点、定向 `edges`、类型；边来自可解析的 `[[wikilink]]` | 作为“引用 / 被引用”的明确关系，按 `path` 定位；边不包含句子级证据 |
| 页面来源 | 图节点的 `sources` 来自页面元数据，摘要还可能从 `full_text` 写入来源；现有 Demo 另有自己的 `sources` 数组 | 展示来源声明；需与资料清单做可靠解析，不能凭名称猜测唯一 `hash` |
| 资料清单及阅读 | `POST /api/v1/list` 提供资料 `hash`；`POST /api/v1/document/source` 按 `hash` 读取可用正文 | 资料以 `hash` 标识；处理状态需依据真实操作结果，不能沿用 Demo `phase` 当服务字段 |
| 页面阅读与单页链接 | `POST /api/v1/page` 读取正文；`POST /api/v1/page/links` 返回出链、入链 | 局部详情可按需加载；与全图结果使用相同关系语义 |
| 质量与影响 | `POST /api/v1/lint` 返回报告文本；资料移除支持 `dry_run` | 报告先作为报告阅读，移除影响使用预览；要做逐项任务卡需先有可定位对象的结构化结果 |

前端可在知识模块中把服务结果整理为“对象、关系、解析状态”供页面使用，但不能把共同来源写回 OpenKB 的显式图边，也不能把 `sources` 的显示名当资料主键。服务协议、错误解释和解析规则留在知识模块；Shell 只负责导航与公共上下文。

本版不宣称自动发现语义相似、事实冲突、因果关系或答案级引用。若未来引入模型建议，最小闭环应为“建议 → 展示原文证据与模型理由 → 人工确认或驳回 → 留下确认状态”。确认前建议与显式关系分层展示；只有相似度分数不能构成可靠关系。

## 6. 版本安排

**第一阶段：关系可信、路径可用。** 接入显式知识链接及来源声明，完成对象解析、来源不可用状态、文本搜索入口、局部关系、理由面板、阅读返回、深链接和移动端列表。保留现有内容管理功能。记忆实验页同步收敛为筛选与详情，不继续使用无真实关系的连线。先覆盖“找到—读到—说清关系”的闭环。

**第二阶段：影响与维护。** 在资料和页面详情加入关联摘要；联动资料移除 `dry_run` 与单页链接接口。展示确定性待处理项：失效引用、不可解析来源、编译失败。若质量报告仍只有文本，先提供报告与手动定位，不做虚假的可点击问题计数。

**第三阶段：辅助发现。** 在有真实用户场景和可评估样本后，再试相似内容、冲突候选、跨资料发现。建议可撤销、可解释、可评价；是否需要跨记忆和知识库关系，先验证身份范围、权限、来源和生命周期语义。

## 7. Demo 设计残留清理清单

正式实现时清理现有试验入口与旧图谱的重叠表达，避免用户看见两套互相矛盾的“关系”。这些文件当前可能含未提交工作，清理应在实现迁移并验收后进行。

| 残留 | 处理原则 |
| --- | --- |
| `packages/knowledge-app/src/Graph.tsx` 的全局静态网格与 `getRelations` | 用真实显式链接和局部视图替换；共同来源保留为单独的派生线索，不再作为整张图的唯一边 |
| `apps/shell/src/design-study/` 与 `/content-study.html` | 吸收已验证的搜索、路径、阅读和响应式交互后，移除实验入口、重复样式与测试；不保留双份业务状态机 |
| `MemoryStudy.tsx` 中“用户 → 分类 → 记忆”的连线 | 将身份、范围与分类还原为筛选和导航；保留原文、状态、历史与修正能力，不称为记忆关系图 |
| `packages/knowledge-app/src/demo.ts` 的内存数据、虚构状态与失败正文 | 正式路径从服务读取；示例数据只进入隔离的开发夹具，不进入用户可见的生产状态 |
| “预设示例”质量报告与模拟成功进度 | 接真实报告和服务结果，或隐藏相应动作；不展示看似真实的错误数、检测结论或计时器成功态 |
| “知识图谱”文案、来源关联标签与旧测试选择器 | 统一关系词汇和统计口径，更新测试以验证关系语义、路径、错误状态与移动端可读性 |

迁移时先确定唯一正式入口与对象 ID，再接真实数据，随后删除旧组件和演示数据依赖。现有文档 `2026-09-29-content-browsing/plan.md` 描述的是独立实验页的交互验证；完成迁移后应标注其历史范围，避免被当作正式产品规格继续扩展。

## 8. 验收与效果

第一阶段的验收样例至少覆盖：有显式链接且有可读来源、只有共同来源、无来源声明、来源名称找不到资料、同名来源不能唯一解析、资料正文不可用、无近邻、空库和大量近邻。逐项确认关系标签、解释、去向和返回；切知识库、刷新和浏览器前进后焦点一致。重点验证移动端不靠连线传达唯一信息。

产品效果不以“图谱节点数”衡量。建议记录匿名聚合指标：从搜索或详情进入关系后打开原始内容的比例、从页面到来源的完成率、从资料进入影响预览的比例，以及“关系解释”后的退出或继续阅读情况。配合小样本任务测试，让用户分别判断一条显式链接和一条共同来源线索；若多数人把后者误读成语义支持，就需要改文案和布局，而不是增加图形复杂度。

前述章节给出产品目标与验收口径，具体落地状态见下节。验证按知识模块的最小受影响测试、WebUI 测试集、类型检查、构建与差异检查进行。

## 9. 2026-09-29 落地记录

正式知识页已接入 OpenKB 的知识库清单、内容清单、图数据、正文读取、页面保存、文件导入、重新编译、质量报告与资料移除预览。关系页按显式链接、声明来源和共同来源线索分组；概念页指向摘要页、摘要页指向资料的链路按服务元数据解析。资料清单新增相对来源路径与文档名，移除和重编译使用稳定 hash 定位。独立设计实验入口、旧静态全图、知识示例数据和预设质量结论已清理。

本轮未接入 Mem0、对话答案级引用、模型提出的相似或冲突建议，也未实现大规模库分页与完整 Markdown 渲染。这些能力分别依赖身份权限、可定位证据或新的数据规模与阅读要求；不得以当前共同来源线索替代。

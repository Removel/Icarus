# DeepSeek 前端分析与 Icarus 对应建议

这是 2026-10-22 对实际生产 JS/CSS 的静态分析补充，主方案见 [plan.md](plan.md)。仅讨论对话布局与交互，不讨论调用 DeepSeek 私有接口。编译变量和哈希类名只用于提供可核对的证据。

## 分析方法与限制

1. 在用户已登录页面读取运行 DOM 和计算样式，确认真实加载的资源。
2. 从公开静态资源地址下载 `main.a34f79a498.js` 与 `main.4591aecc90.css`，在系统临时目录格式化 JS 后按组件、样式映射和调用关系检索。
3. 将分析结果与 Icarus 的 `ChatApp`、`ChatTranscript`、`ChatProcess`、`ChatReasoning`、`useChatText`、会话 hook 和现有测试对照。

JS 中保留了 CSS module 的属性名、部分 DOM 类名、状态字段和方法名，可以恢复模块职责与行为线索；压缩后的局部变量名无法证明原始组件命名。未执行下载的生产代码，未提取用户凭据，也未发送测试消息。

没有 `sourceMappingURL` 指令不等于证明所有 source map 都不存在，本次没有枚举猜测其地址。编译产物分析足以支持当前布局可行性评估；上线行为仍需实际交互验证。

## 消息列表：虚拟化与滚动跟随是两套逻辑

可定位符号：`ds-virtual-list`、`ds-virtual-list-visible-items`、`submitScrollAdjustingTask`、`getOffsetTopOfKey`、`requestFollowScroll`、`forceScrollToBottom`。

底层列表负责可见范围、条目尺寸与 key 定位。尺寸更新时，代码读取条目 `offsetHeight`，与旧高度相减，更新高度记录；随后视情况通过 `scrollBy` 或滚动调整任务补偿位置。移动端还有触摸期间的临时位移补偿与恢复分支。由此可见，它的稳定阅读位置并非单纯依赖浏览器默认滚动锚定。

上层跟随控制器另外维护是否自动跟随，并提供以下职责：

- `onUserScroll`：依据当前位置更新是否跟随。所查版本使用约 1px 的底部判定容差。
- `requestFollowScroll`：只有仍处于跟随状态时，才提交并执行滚动调整。
- `forceScrollToBottom`：明确启用跟随并滚到列表底部，供用户点击返回底部等动作使用。
- 返回底部按钮的显示采用另一个约 52px 的距离判断，与跟随状态的判定不相同。

还有一个值得注意的细节：代码会在特定条件下取当前生成中助手回答的 `.ds-assistant-message-main-content` 起点，与底部目标比较。若继续到底会越过该正文起点，就将目标限制在正文起点，并停止这一轮自动跟随；同一会话/消息记录已处理状态。包含思考内容时，定位回答也会寻找正文起点，而非始终定位整条消息的最顶部。这解释了它为什么对“较长思考之后开始回答”做了专门处理；本次没有运行生成来确认所有触发场景。

以下是依据代码概括的职责示意，不是恢复出的原始源码：

```text
消息/思考内容增长
  → 更新条目尺寸
  → 列表补偿尺寸变化
  → 若仍跟随：计算本次滚动目标
       → 底部，或特定条件下限制到回答正文起点

用户向上阅读
  → 退出跟随
  → 后续内容增长仍可更新尺寸，但不主动拉到底部

点击返回底部
  → 强制到底并重新跟随
```

**Icarus 对应：**`ChatTranscript.tsx` 已维护 `follow`、`followedTop` 和 `away`，用户离开底部后不抢位置；`ChatProcess.tsx` 的内部过程窗口有独立跟随逻辑。当前没有上述虚拟列表和正文起点限制策略。

**实施建议：**首版保留已有滚动语义，将“正文起点限制”和“虚拟化”分别作为可选后续项。前者改变产品行为，需要单独约定；后者需依据长对话的 DOM 数量与渲染耗时决定，不能为了模仿布局一起重写。尤其不能把跟随阈值从 64px 机械改成 1px，就认为复制了它的阅读体验。

## 输入区：镜像测量、底部工具行与响应式收缩

可定位符号：CSS module `5744` 导出的 `inputFullContainer`、`inputWrapper`、`textareaAlignWrapper`、`textareaMirror`、`functionRowLeftColumn`、`functionRowRightColumn`。

组件职责可概括为：

```text
底部 sticky 容器（另有渐变背景）
└─ 输入卡片
   └─ 纵向内容容器
      ├─ 文本高度容器
      │  ├─ textarea
      │  └─ 隐藏文本镜像
      └─ 工具行
         ├─ 左列：思考/搜索等切换
         └─ 右列：附件/发送或停止等操作
```

代码中，文本镜像取输入文本的前 20000 个字符并补一个换行，用来承载高度；这是镜像内容的处理，不能据此断言输入或请求只能有 20000 字符。镜像 CSS 为 `visibility: hidden; pointer-events: none; max-height: 336px`，textarea 叠放在同一个相对定位容器内。尺寸观察器监听镜像变化，刷新滚动状态；textarea 滚动时也会更新是否到底的状态类。

工具行会先把文字显示出来测量，再根据父容器是否溢出、子项文字是否换行，选择显示或隐藏文字。其响应式行为因此不只是固定断点 CSS。

键盘代码显式处理组合输入，非组合输入时：空输入的 ArrowUp 请求历史值；Enter 且无 Shift 时进入提交分支；Ctrl/Alt+Enter 的代码分支插入换行；移动端普通 Enter 不走桌面提交分支。这些是该版本的具体行为，不能自动作为 Icarus 新需求。

**Icarus 对应：**`ChatApp.tsx` 已使用 Semi `TextArea autosize={{ minRows: 1, maxRows: 5 }}`，并同时检查 `isComposing` 和 keyCode 229。输入卡片、内部工具行、停止、引导和执行中排队也已存在。

**实施建议：**先用 Semi 的自动高度做视觉优化，调整输入卡片的空间、边界、文字行高与工具排列。默认保留 Icarus 现有 Enter 排队语义；手机的回车行为若要变化，应作为明确交互改动。只有 Semi 无法满足具体高度或滚动要求时才引入额外测量逻辑。

## 思考内容：单独片段，仍有自己的渲染与定位

可定位符号：`useThinkFragment`、`useIsWIPThinking`、`ds-think-content`、`ds-assistant-message-main-content`。

所查代码按 session/message/fragment 获取思考数据，利用工作中状态选择活动或静止图标，并将思考内容交给单独的富文本渲染分支。显示层同时能取得正文容器，因此导航时可区分“到这条消息”和“到回答正文”。

**Icarus 对应：**已有任务级过程分组和独立思考组件，展示状态与文本渐进显示分离；收起后重新展开不会重播文本，历史默认折叠。这套能力适合继续使用 Semi `AIChatDialogue.Reasoning`，主要优化分组间距、标题、层次和定位。

## 会话栏：按时间分组，不应顺带复制所有能力

可定位字段：`todaySessions`、`yesterdaySessions`、`days7Sessions`、`days30Sessions`，以及对应时间段标签。渲染代码对空分组不显示标题；滚动和尺寸变化会触发加载/视口检查。代码还包含置顶分组折叠和批量选择相关路径。

**Icarus 对应：**当前列表有标题、时间字段、搜索、新建、删除和选中项位置保护，可以先通过客户端按时间分组改善扫描效率，无需为布局新增后端服务。分组用哪个时间字段、如何处理时区与无效日期、搜索时是否保留组标题需要明确。

会话置顶、重命名、远程搜索与批量管理应分别核对 Gateway 已有契约再定范围。布局目标不自动包含它们，也不能把 DeepSeek 的会话树/分支结构强加给 Icarus。

## 真正影响当前观感的布局差异

当前 Icarus 并非缺少居中限宽：`chat.css` 已有 800px 正文上限、居中的输入区和用户消息气泡。更明显的差异是可用空间和页面层级：

- 全局导航展开为 208px，对话内部会话栏又占 248px，消息区还受页面左右留白和内部边界限制。
- 全局顶栏、工作区连接表单、对话标题分别占据一层纵向空间。
- 对话工作台有完整外框，内部会话栏、输入卡片也有自己的面板样式。

因此优先顺序应为：**减少重复导航占用 → 整理顶栏与工作区入口 → 减少嵌套面板 → 微调消息排版和输入卡片**。将正文上限从 800 改到 840，并不能单独解决空间问题。

建议先保留 shell 与 chat-app 的状态所有权，用紧凑的全局导航配合对话会话栏验证；如果后续决定将两类导航合为一栏，再设计明确的组合接口。不要为统一视觉把会话 hook 放进 shell 或复制到两个位置。

## 工作量结论

沿用现有 Semi 与业务能力，完整首版估算仍为 **5–8 人日**，桌面视觉预览约 **2–3 人日**。主要不确定性是手机导航形态、侧栏是否合并，以及是否额外要求 DeepSeek 的正文起点滚动策略、虚拟列表或会话管理新能力。

本文记录调研阶段的分析，没有执行模型请求。后续首版实施与浏览器回归结果见 [布局优化记录](plan.md)；静态代码分析本身不代表 DeepSeek 交互验收通过。

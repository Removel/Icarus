## 已有形态

核对 `apps/rela-mem/src/api/`、Agent relationship 插件及其测试后，rela 在当前仓库的职责是人物身份、稳定档案、圈子和有方向的关系。它是独立 HTTP 服务，自身不调用模型。Agent 已有 find/context/remember/forget/relate 五个工具，插件为可选启用；不是等待前端实现才存在的能力。

事件与经历归记忆，文档及派生内容归知识库，人物稳定事实和关系归 rela。Person ID 表示服务中的人物，姓名只用于候选搜索；同名人物不能自动合并。Agent 的使用边界见 [relationship 架构](../../../../agent/docs/spec/2026-10-18-relationship-plugin/arch.md)，服务契约见 [跨应用契约](../../../../../spec/2026-10-19-agent-relationship-integration.md)。

## 已确认的入口与布局

用户已确认：将「知识库」「记忆」「人物」放入左下角现有账户菜单，与「系统设置」同级。点击前三项进入主区域的管理页面；系统设置保持现有交互。不新增常驻「工作台」按钮或一层子菜单。当前代码已完成入口迁移。

用户关注约 330px 侧栏的空间占用，未采用顶部一排三个入口或竖排三个常驻入口。新版布局保留对话侧栏，并延续记忆、知识库的管理页节奏。

人物页首先管理 Agent 认识的人，首页优先支持浏览与辨认，因此使用卡片网格。2026-10-28 根据实际截图反馈，方形比例调整为紧凑身份卡片：列宽上限 280px、内容自然决定高度；36px 头像旁将姓名和类型标签同排，别名与 ID 紧随其后，无别名不占位。移除底部分割线与跳转箭头，字体沿用公共无衬线体系。卡片仍只展示姓名、类型、别名和简短 Person ID，独立标识归档；长文本限行，完整内容留在详情，不增加关系数、完整度或活跃度。

宽主区域三列、中等宽度两列、窄屏一列；列数按实际内容宽度决定，计入侧栏和内边距。移动端默认一列，足够宽时可两列。搜索、类型/归档筛选、「人物 / 圈子」分类和游标分页语义保持既定设计。

详情继续采用弹窗阅读式档案，保留稳定档案、关系、圈子、别名与身份核对四分类，以及关系跳人返回和列表上下文恢复。人物与圈子弹窗统一为桌面宽 860px、手机全屏，标题/身份/分类/正文共用左侧基线；浅底头部、整体可复制的 ID、次级编辑按钮和实心添加按钮形成层级。分类左对齐，不重复档案标题；空状态增加操作提示，单页隐藏分页，翻页后的空页保留上一页。旧 [layout.html](layout.html) 与早期方案仅为探索记录；新的卡片决策不等于恢复早期方案中的分栏、字段或交互。

内容设计帮助用户通过姓名、别名和 `Person ID` 区分人物，并查看档案、圈子、关系和来源。关系使用「张三是李四的同事」等明确自然语句，保留方向，不按端点顺序或共同关键词推断。

例如用户说「小王是我的同事，喜欢咖啡，昨天一起吃了饭」：人物页负责同事关系和稳定偏好，昨天吃饭属于记忆。前端不自行分类、推断或复制数据；由 Agent 使用已有工具完成。一个人的资料可以由用户查看和纠错，不能只存在于模型提示词中。

圈子保留一级分类，首页按内容宽度显示两列或一列紧凑卡片，复用人物的图标/身份结构，展示名称、类型、可选负责人 ID 与圈子 ID，不强制方形，不使用无负责人占位或跳转箭头。详情采用阅读式弹窗，成员按姓名、类型、圈内别名、角色、身份说明与完整 ID 排列，支持加入、编辑与退出。人物档案中的所属圈子仍为只读信息。

## 实施边界

代码归 `apps/webui` 的人物应用包。Node/Vite 同源代理固定的 rela 服务前缀，在服务端附加 Token；浏览器不持有服务凭据、不直接连接 FalkorDB/PostgreSQL。复用现有统一工作台和控件，不新增一套配置/身份库。

实施前核对每个服务端 API 的分页、身份、归档、档案墓碑和关系失效语义；缺少的服务能力由 rela-mem 拥有，不在前端模拟。Agent 继续通过 relationship 工具访问 HTTP，不绕过插件层，不把 UI 状态或人物查询逻辑塞进 ReActAgent。

验收覆盖同名、长姓名/多别名、ID 区分、卡片列数、主题、空结果、服务不可用、游标/截断、正反称谓和路由恢复。写入阶段另测冲突、部分成功、结果未知、墓碑与失效后的可追溯读取。各阶段按最小测试、WebUI 套件、类型/构建/差异检查的顺序验证；命令与环境前提见实施计划。

保留现有工作区改动，不用生产人物作 fixture，不把历史静态稿验证记为新卡片或生产验收。未经明确请求不创建分支、提交、变基或推送。

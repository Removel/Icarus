# Argus 功能定位与第一阶段设计

> 状态：2026-10-21 讨论确认的目标设计；第一阶段代码已在工作区实现，当前源码说明见 [arch.md](arch.md)。
> 本次修订以现有 QQ 代码、测试及应用级生命周期管理为迁移基线，替代旧稿中决策图、回放、
> 永久 accepted、启动恢复和运行中逐条追加的要求。具体文件、接口和测试见 [plan.md](plan.md)。

## 1. 定位与职责

Argus 是 Icarus 的常驻感知入口：持续观测外部信息源，保存事实，从大量消息中判断哪些值得
交给 agent 处理。QQ 是第一个来源，不是 Argus 的业务边界。

- Argus 决定是否叫醒，不决定 agent 应当说什么、做什么。
- Argus 不生成、不发送平台回复，不执行外部动作，不维护语义记忆。
- 观测、判断、递交和解决记录属于 Argus；真实会话、run、上下文装配和工具执行属于 agent 侧。
- 不新建 agent/runtime，不共享其他应用的数据库或业务表，不绕过 Gateway 直接访问 agent 数据。
- 动态观测内容进入未来 agent 的当前 User Prompt，不修改稳定 System Prompt。

本文中的 agent 指实际执行任务的 agent 核心。第一阶段用明确标注的 mock 代替它，不代表已经
实现了真实会话和外部行动。

## 2. 第一阶段交付范围

完成可以持续运行的闭环，而不只停在收到唤醒请求：

```text
收集 QQ 上报 → 保存观测 → 成组与判断 → 递交请求 → mock 接收并处理
    → 显式返回解决结果 → 保存结果并关闭请求 → 继续判断后续消息
```

这一阶段包括：

1. OneBot 上报鉴权、解析、幂等、内容版本和撤回。
2. PostgreSQL 中的观测与叫醒请求持久化、统一查询接口。
3. 群聊去抖、规则筛选、必要时 Jev 语义选择；普通私聊直接成为叫醒信号。
4. 有限预算、长消息短摘录和完整原文读取。
5. 递交、接收、解决的状态区分；同一聊天对象串行、不同聊天对象独立处理。
6. mock 的成功、延迟、失败和重复结果测试，以及运行期间的有限重试。
7. 适配当前 Icarus 的应用级启动、停止、状态和健康探针。

明确不做：决策图接入、规则/历史批次回放、真实 agent/Gateway 唤醒方法、会话 kind/scope、
运行中追加上下文、行动日志、真实动作核对、接管租约、权限档位动态修改、记忆整理、其他平台。
旧 decision_graph 源码可保留为独立存量代码，但新链路不使用它。

## 3. 业务模块与经典 Python 后端分层

采用“按业务模块分包，模块内部经典分层”：

- `core`：配置、数据库等基础设施。
- `common`：统一观测、规则判断、叫醒、结果记录与后台调度。
- `surfaces/qq`：QQ 来源，内部使用 `api`、`schemas`、`services`。
- 数据持久化使用 `models`、`repositories`；外部调用使用 `clients`；后台扫描使用 `tasks`。

不为目录对称创建空层。QQ 没有专属业务表，因此不创建 QQ 的 models/repositories；不额外
建立重复的 entity/contracts/dto 类型体系。ORM models 不直接作为 HTTP 响应或外部调用参数。

依赖规则：来源之间不互相 import；common 不 import 任何具体来源；只有装配入口了解 QQ
实现。来源声明最小事实构造接口，规则和 common 使用规范化事实，不识别 QQ 协议字段。
每个 Python 包有 `__init__.py`，但包导入不启动服务或注册后台任务。

## 4. 观测、身份与重启

### 4.1 观测记录

- 每条平台消息的每次有效内容变化保存为一条新 revision，不覆盖历史原文。
- 消息身份为 `(source, chat_id, message_id)`；revision 从 1 递增。
- QQ 的 chat_id 包含平台、机器人账号、群聊/私聊类型和外部目标，避免跨账号混淆。
- 相同内容重投不新增 revision，也不重复通知调度；并发重投仍必须成功去重，不能返回 500。
- 撤回新增 `deleted=true` 的版本，不参与后续判断。撤回先于原消息到达也能保存墓碑。
- QQ 没有可靠的修改事件序号，采用保守规则：已见过的相同内容视为重投；撤回后到达的普通
  消息不能复活该消息。暂不支持同一消息内容 A→B→A 被识别为第三次有效修改。
- 判断期间收到修改/撤回，在落判断结果时重新校验版本；失效选择整批放弃写入，下轮重算，
  不能把旧版本继续递交。已递交后发生的撤回仅记录事实，第一阶段不取消 mock 工作。

### 4.2 本次启动范围

每次应用启动生成新的 `boot_id`。本次收到并成功新增的观测版本标记为该 boot_id。

- 只调度本次启动的消息，不恢复上一次遗留任务，不主动拉取历史，不使用旧批次作为判断上文。
- 相同旧消息在新启动后重投，仍按全库消息身份去重，不因为换 boot_id 再处理一次。
- 旧观测和请求保留可查询，原状态不伪造为已解决；查询明确标注不属于当前启动、当前不活跃。
- 旧 accepted/waiting 不占本次启动的聊天对象，不需要启动时批量修改旧状态。
- 运行期间的递交失败仍按有限重试处理；“不做启动恢复”不等于“运行期间不处理失败”。

这是有意选择的非持久任务恢复语义。若在停机前刚收到消息，该消息不会在下一次启动自动补做。

## 5. 群聊与私聊的处理时机

### 5.1 群聊

同一个群里一次只处理一个叫醒请求，但不是每条消息都交给 agent。

- 普通消息累计到安静 5 秒，或最长等待 30 秒后，进行一轮批量判断。
- `@` 或叫机器人名字是强信号，空闲时尽快进入下一轮判断，不等待安静窗口。
- 有请求正在递交或处理时，新消息继续保存，不追加当前请求，也不创建第二个并行请求。
- 当前请求进入终态后，重新检查积累消息：普通消息仍按去抖规则处理，强信号不丢失。
- 后续批次只有再次命中规则才递交，普通闲聊标记忽略，不因为队列非空就自动叫醒。
- 其他群、私聊有各自的处理进度；一个群的模型/处理耗时不阻塞所有来源。

例子：正在总结文章时，群里来了“吃什么”“吃火锅”和“@Icarus 看看报错”。先把三条记住，
文章处理完后再判断这三条；闲聊不单独递交，报错请求可以触发下一次工作。

### 5.2 私聊

普通私聊即为明确寻址，不要求叫名字，也不调用 Jev 判断是否值得回应；通过基本门槛后尽快
叫醒。相同私聊对象仍遵守一次一个请求。它忙的时候新私聊先保存，结束后处理下一批。

直接叫醒不绕过验签、去重、自消息排除、敏感过滤、预算及来源开关。`qq.enabled=false`
表示暂停 QQ 来源，不挂上报入口、不扫描 QQ 存量、不调用 Jev 或 mock。

## 6. 规则与判断

- 判断由显式代码、Git 版本化 YAML 规则及来源事实构成，不使用决策图，不建设回放系统。
- 机械规则能决定的情况不调用模型；Jev 先回答 `can_speak`（是否适合说话），再回答 `speak_now`（现在就说吗）；两次都是 yes 才唤醒。
- 语义判断使用按时间排序的窗口，每条包含发送者、文本、时间和 `current` 标记；Icarus 自己的消息作为上下文出现，但不作为当前候选。
- 理由来自规则文字；Jev 不生成自由文本理由，不负责字符解析、成组、去重、记账或路由。
- 默认沉默；Jev 超时、失败、非法选项或任一问题为否均不叫醒，并保存可读原因。
- 硬门槛在规则前执行：非最新/撤回、已保留给其他请求、自消息、敏感内容、来源关闭及静态
  权限不足。自消息与敏感消息逐条排除，不连带丢掉同批合法消息。
- 敏感检查覆盖完整当前消息及所有拟送 Jev 的上文，先检查再摘录，避免截断隐藏敏感词。
  命中敏感词的历史上文不发送；不追求关键词以外的彻底语义安全判断。
- Jev 输入只包含必要的短文本和时间；显示名保留在观测里但不外送，避免名称绕过过滤与预算。
  不发送定位字段、账号标识或数据库连接信息。模型置信度和概率必须是有限且合法的数值。
- 记录命中规则、规则版本、观测引用、模型选择、错误类型等解释信息；这不构成回放承诺。

保留静态权限配置，默认档二。第一阶段不执行真实动作，因此档位只是判断证据和准入条件，
不是已实现的完整动作授权系统。档位 1 允许观测/认知类工作；小于 1 禁止递交；不得宣称
mock 可以验证档位 3～5 的真实动作授权。

## 7. 预算与原文

- 每轮最多选择 20 条新消息，按接收时间和稳定 ID 排序；本轮选择和其余待处理消息明确分开。
- 当前消息摘录总预算默认 20000 字符。保留完整原文，摘要不覆盖原文。
- 第一条消息超过预算时，用其前部短摘录参与判断，标注截断，不让超长队首永远堵住后续消息。
- 选入消息的短摘录用于事实构造、Jev 和递交；不会在另一个步骤重新按全量原文判断。
- 群聊上文最多 10 条，另有默认 4000 字符预算；只从同 chat、同 boot 的更早最新版本中取，
  排除撤回、自消息和敏感消息，不挤占当前消息预算。
- 只有本轮实际选中的 ID 可被忽略、关联叫醒或标记处理；预算外记录保持 new，等待后续判断。
- 强信号在预算后面时，不提前消耗它。待前面的有限批次处理完后，该强信号仍能触发判断。
- 递交包含 wake_id、观测 ID、位置、简单理由与短摘录；完整观测可通过 Argus 规范化读接口查询。

第一阶段处理单元是同一个 chat 的有限消息批次，不建立 thread/event 聚类系统；真实 agent 的
更深工作单元划分留待后续设计。

## 8. 递交、解决与有限重试

### 8.1 状态区分

叫醒请求的活跃状态为 `waiting`、`sent`、`accepted`，终态为 `resolved`、`no_action`、`failed`。
活跃唯一性只约束同一 boot_id、同一 chat_id。

- waiting：已持久化并保留消息，等待递交或重试。
- sent：一次递交尝试正在进行，不能据此声称已被接收。
- accepted：接收方已确认接收，等待显式结果，不能永久停在这里。
- resolved：接收方显式报告已解决；no_action：显式报告无需动作；failed：终止失败。

观测区分 `new`、`delivered`、`processed`、`verified`、`ignored`、`failed`：

- 为 wake 保留消息时仍是 new，但有 wake_id，不再被其他判断选中。
- 确认接收才置 delivered；有效解决或无需动作结果置 processed。
- 硬门槛或规则忽略置 ignored；递交最终失败、处理失败或超时置 failed，不自动再次叫醒。
- verified 只留给未来真实行动核对，第一阶段不会写这个状态。

### 8.2 重试与结果

- 递交的幂等身份是稳定 wake_id。传输结果未知时，不清空关联再创建新请求；重试同一个请求。
- 默认单次递交超时 5 秒，最多尝试 3 次，间隔 1 秒、2 秒；明确不可重试拒绝直接 failed。
- accepted 后默认最多等 60 秒；查询错误在期限内重查，超时明确 failed 并释放该 chat。
- 接收方必须按 wake_id 幂等，重复递交不重复处理；终态结果重复返回不重复推进。
- 结果必须匹配 wake_id 和完整选中 ID 集合，不能完成别的 chat/批次。部分结果、未知 ID 或
  相互冲突的终态为非法结果，当前请求置 failed，记录原因，不假装解决。
- 进入终态时结果和观测状态在同一事务写入；释放当前 chat 后再判断积累消息。

以上时间、次数是实施默认值，不是用户业务偏好，可在配置中调整；参数必须为有限合法值。

## 9. mock 的范围

第一阶段在 Argus 的外部处理接口后注入 mock，不新增另一个运行时或第二个部署。

- 接口拆开“递交并接收”和“查询显式结果”，测试能够观察 accepted 的等待阶段。
- 默认 mock 接收后短暂等待再返回 resolved，结果带 `simulated=true`。
- 测试可控制延迟、拒绝、超时、失败、重复递交和重复结果，不读取真实 QQ 或模型密钥。
- mock 不创建会话，不调用真实 agent，不发平台消息、不写记忆、不产生真实行动证据。
- 终态结果落库后释放 mock 持有的完整请求；数据库保存审计记录，不在内存无限累积历史。
- mock 的 resolved 只证明 Argus 的状态闭环，不意味着外部问题真的解决，也不能标成 verified。
- 保留已存在且有测试的 Gateway 底层传输迁移，但本阶段不装配、不调用、不注册 argus.wake。
  未来真实 Gateway adapter 需另行设计与 Gateway 应用文档承接，不预写假的成功 RPC。

## 10. 存储与生命周期

- 单 FastAPI 进程，不拆子容器/子运行时；统一遵循现有 Icarus 应用级生命周期管理。
- PostgreSQL 为唯一运行时和集成测试数据库。两张业务表 observed_items、wake_requests，
  外加 schema_version；结果和重试信息存于请求记录，不增加动作日志等业务表。
- 使用与现有 PG 部署同款 `pgvector/pgvector:pg17` 镜像；Argus 使用独立数据库/账号/表。
- 本地开发和自动测试使用隔离实例/数据库，不访问 mem0、rela-mem 的真实数据；本阶段不修改
  它们的 Compose、账号或数据库。正式 PG 的建库、账号和部署由用户在本地开发完成后手动执行。
- 连接串只通过 ARGUS_DATABASE_URL 提供，不能读取根 TOML 推导密钥；无连接串时明确失败。
- 保留 apps.argus.src.main 入口，支持 lifecycle 传入 host/port；只允许 loopback 绑定。
- /health 供现有管理器探测，/api/argus/health 供统一接口，二者调用同一健康逻辑。
- 停机先停止接收，取消并等待本进程任务，再关闭自有客户端和数据库。启动中失败也须释放资源。
- 日志、错误响应不包含密钥、连接串密码或聊天原文；普通测试替换配置并屏蔽真实环境加载。
- 旧 SQLite 不迁移、不再使用；删除旧代码不等于删除旧数据文件，不在本次自动清理用户数据。

## 11. 读接口

第一阶段仅提供本机访问的健康、单条观测、叫醒详情/列表及当前未处理消息查询。历史记录可查，
但必须区分 boot_id 和 active 状态，不能把旧 accepted 展示成正在执行。

列表必须有稳定排序、有限分页和状态参数校验。读取接口不触发判断、不推进处理状态。
未来 agent 深读可以复用这些接口；真实工具、权限、跨应用认证不在此阶段虚构完成。

## 12. 后续阶段

第二阶段的目标设计与逐文件计划现已独立记录于
[真实 Agent 交接设计](../2026-10-21-argus-agent-handoff/design.md)，共同协议见
[跨应用约定](../../../../../spec/2026-10-21-argus-agent-handoff.md)。这些仍是未实现的计划。
第二阶段是通用交接：Agent 自主同群读取/等待与逐项报告，替代本稿第一阶段“整批结果相等”和
真实模式不可用的限制；途中消息看见不等于接手，未报告的途中项仍可后续判断，未报告initial
才保留未解决。第二阶段不接 QQ 动作，不发平台消息。这些属于第二阶段目标，不修改这里对
第一阶段源码行为的历史记录。

第二阶段包含隐藏scope会话、静态/动态上下文装配、逐项结果、持久占用与退出对账；审阅后补齐
完整停止屏障、永久拒绝报告结案、严格单调水位、安全内容出口、正文续读、后台MCP不继承和
远端专用入口。这些仍为目标，不将其写成第一阶段已有代码。
第三阶段再设计真实 QQ 动作：SnowLuma/QQ MCP、通用 MCP 策略、凭证隔离、发送与动作核对。
新增语义记忆或其他租约扩展按后续需求设计；复用现有运行时与persona/mem0/rela-mem/openkb
契约，不建设 Argus 专用语义记忆。

真实接线前必须明确身份认证、动作授权、会话结束、处理超时和结果证据。是否支持运行中追加、
持久任务恢复、thread 聚类需要新需求，不从本阶段 mock 或旧 design 自动继承。

# Argus 判断层：批次与判断图设计

> 状态：设计待评审，尚未实施。本文描述目标形态，不代表当前源码已有这些能力；现状以 `2026-09-29-qq-observation-flow/arch.md` 与代码、测试为准。
> 本文**修订** `2026-09-29-qq-observation-flow/design.md` 的三处结论：判断单元由"一条消息"改为"一批消息"；废除 300 秒过期规则；提交与提交未知状态由 observation 移到批次。

## 为什么要改

现已上线的链路是"一条消息 → 一次判断 → 一个 wake/silence"，真实跑通且可用。但真实观测暴露了三类不足：

1. **成本与判断单元不匹配**。群里一轮 15 条消息触发 15 次模型调用，全部判为 silence——钱花在"判断不回复"上。人读群消息也不是看一条回一条，而是扫一段近况流再决定。
2. **单条消息判断会看漏**。两条各自无意义的消息合起来才需要回答；一条消息在补充上一条正在处理的内容；积压消息需要连起来看；跨较长时间的内容需要拼历史。这些在"单条即单元"下无法表达。
3. **动作不止"叫/不叫"**。正在回复时来的补充消息应当并入在跑的任务，而不是新建一个任务。

## 判断层的定位与红线

判断层只回答**注意力与路由**问题：这条内容是不是对我说的、值不值得插话、它属于哪段正在进行的对话、还有没有时效。它**不回答内容问题**（该说什么、怎么说），也不产生副作用。

红线：

- **只回答注意力/路由问题**；内容理解与回复由 Icarus 承担。
- **判断逻辑以只读为主**：允许过程中读取外部信息（历史、将来的记忆与知识），但不发送、不写入外部系统。
- **模型只给答案与分数，阈值与闸门写在代码里**。
- **确定性节点零成本，先跑；能定就收工**。

## 一、判断单元：批次

### 分组规则（确定性，不花模型钱）

**分组键 = 会话**（subject）。私聊的会话就是一对一对端，天然自洽；群聊里同一段时间本来就混杂多人，按发送人切会把"两个人接着说同一件事"切散。发送人身份随每条消息带在转录里。

**批次 = 该会话自上次判断之后累积的一段消息**，由下列条件之一关闭并触发一次判断：

| 关闭条件 | 群聊 | 私聊 |
|---|---|---|
| **明确对着机器人**（被 `at`、正文叫出机器人名字） | 立即关闭，不等停顿 | 立即（私聊即对机器人说） |
| **静默**：该会话连续 `batch_quiet_seconds` 无新消息 | 默认 5 秒 | 不适用 |
| **上限**：批次达到 `batch_max_messages` 条，或距开批 `batch_max_seconds` | 默认 20 条 / 60 秒 | 同左，作为保护 |

三点含义：

- **立即关闭时批次包含开批以来累积的全部消息**，不只是触发那一条——这样"两条合起来才该回复"仍然成立。
- **静默关闭是常态**：一段话说完判断一次。
- **上限是热闹群的保护**：再吵也最多每分钟一次判断，而不是每条一次；长时间停机后的积压也不会变成一批几百条，而是被切分成多批。

### 边界情况

- **机器人自己的消息**：照常留档并**进入批次**——它本来就是这段近况流的一部分，人看群消息时也会看到自己的话，而且它可能正是后一条人类消息的上下文。**只有机器人自己消息、没有任何人类消息的批次**由确定性节点直接判 `silence`，不产生模型调用，这就是回环防护。
- **迟到与积压**：并入当前**尚未判断**的批次；**已判断的批次不回头**，靠会话上的**判断水位**保证，避免补入恢复时重复判断、重复唤醒。
- **重启恢复**：**不恢复内存中的批次**。未判断的消息由"该会话水位之后的消息"按同一套规则重新成批即可，批次可从数据库重建。

### 判断水位

每个（平台, 账号, 会话）保存一行水位：`judged_through`（最后一条已并入某个**已判断**批次的观察）。成批只取水位之后的消息；补入循环也以水位为准，因此恢复是幂等的。

## 二、数据模型改动

批次成为**判断与提交的单位**：

- 新增**批次**记录：所属会话、开批/关批时间、覆盖的消息范围、以及判断与提交的**生命周期状态**（`judging / submitting / submitted / submission_unknown / finished`）。**未关闭的批次不必持久化**——它由"会话水位之后的消息"随时重建；批次在关闭、进入判断时才落库，因此重启不会丢失未判断的消息，也不会留下悬挂的批次。
- `observations` 回到**纯事实**：保留来源去重与内容，增加一个"归属批次"的引用；**不再承担提交状态**。
- `submission_id` 使用**批次 id**（稳定、可重试、可对账）；一条消息不再各自提交。
- `session_links` 增加**在跑任务 id**（可空），供动作选择判断"是否有正在运行的任务"。
- 提交给 Icarus 的内容从"一条消息 + 回复提示"改为**该批次的转录**（含各自发言人），并附带回复目标提示。

迁移方式：现有 `argus.db` 中的历史记录保留，不做数据迁移；恢复逻辑按新表结构工作即可（旧记录不再有未完成状态需要恢复）。

## 三、判断节点

**一个节点 = 一个判断**，不限于模型判断；确定性规则也是节点。

节点声明：

- **名字**与**版本**（写库用于排查，例如 `qq-self-message@1`）；
- **需要的材料**：当前批次、会话的近期上下文与水位、会话关联与在跑任务状态，将来的记忆/知识检索结果；
- **可能给出的结论**：`continue` 或若干**终态**；
- **产出的事实**：供后续节点使用，也写入本轮运行记录。

节点产出三类信息：**结论**、**原因**、**贡献的事实**。模型节点另有：它问的问题原语（选一个 / 打分 / 判有无实质内容）、原始答案与置信度/概率。

### `continue` 的语义

`continue` **不是整个运行的结论，而是节点级信号**："这一步不下结论，交给后面"，同时可以贡献事实。它不会自己变成 wake——只有当后续节点接过去并给出 wake 时才会 wake。若**没有任何节点给出终态**，运行落到图自己的**默认终态**，默认值为 `silence`（保守方向：没人拍板就不打扰）。

### 终态词汇

节点级信号为 `continue`；**终态为 `silence`（不打扰）、`wake`（介入并新建任务）、`steer`（介入到在跑任务）**。`wake` 与 `steer` 的分工：`qq-correspondence` 只决定"要不要介入"（`silence` 或 `wake`），`qq-action-select` 在"要介入"之后决定新建还是并入，输出 `wake` 或 `steer`。是否新增"只记录""稍后再看"留待真实需要。

### 失败与超时

节点失败或超时**默认收工**，产出默认终态并打 `warn` 日志。**"因故障收工"与"模型判为不回复"必须分开记录**（现有实现分别对应 `judge_fallback` 与 `judge_silence`）。

已知副作用：取材料的节点失败也会收工——记忆/知识库不可用时，一条明确叫机器人的私聊也会不回复。方向保守，是否按节点类别改为"故障降级继续"另行决定。

### 运行记录

一次运行记录：走过哪些节点（含顺序）、各自结论与原因（终态/continue）、贡献了哪些事实（键名，不记录正文）、谁最终拍的板、是否因故障收工、以及用到的策略/节点版本。这份记录是将来调策略的依据，也是排查"为什么这条没回"的唯一入口。

## 四、图语义与执行器

节点间存在两类关系：

- **可以一起判断**：材料相同、答案互不依赖、各自单独有意义 → 合并为**一次调用**问完（模型接口支持一次带多个问题），不拆节点。
- **必须先后判断**，原因有三：**答案依赖**（后一问依赖前一问）、**材料依赖**（后一判断需要新取的材料，且取什么取决于前面的结论）、**成本闸门**（先跑零成本判断）。

这三种关系构成的是**图而非链**：存在扇出（一个结论被后续多个节点使用）、扇入（一个节点依赖前面多个结论）、条件边（下一步由前面结论决定），以及"取材料 → 判断 → 材料不足 → 再取"的**带环路径**。

**执行器采用最小实现**：按依赖顺序执行；**同一材料只取一次**；遇终态短路；允许**有界循环**（迭代上限写死在执行器，防止反复取材料）；记录运行路径。

**执行器不做**：并行分支调度、检查点与跨进程恢复、运行中暂停与人工介入、图构建 DSL、配置化拓扑。运行存活时间以秒计，可靠性由 `argus.db` 与既有恢复机制承担。

### 为什么不上 LangGraph

需要的是图语义的一个子集（依赖解析、结果复用、条件边、有界循环、路径记录），量级约百来行；LangGraph 强的部分（持久化检查点、跨进程恢复、中断、并行分支、子图）恰好是本期不需要的，引入它还会带来第二套运行状态权威（我们已有 `argus.db`）以及另一套错误与超时语义。**节点契约与引擎无关**，将来若需要，只换执行器。

**重新评估的判据**（满足任一再考虑引入）：需要并行分支 + 扇入；需要判断运行跨进程重启后继续；需要运行中途暂停等待外部输入。

## 五、第一批节点

把现有行为按上述契约重写，用来验证契约表达得下今天的行为：

| 节点 | 性质 | 结论 | 说明 |
|---|---|---|---|
| `qq-self-message` | 确定性 | `silence` | 机器人自己发的消息；不参与成批 |
| `qq-batch-facts` | 确定性 | `continue` | 从批次提取事实：会话类型、是否私聊、是否被 `at`、正文是否叫出机器人名字（NFKC + casefold 归一化，仅文本片段） |
| `qq-correspondence` | 模型 | `wake` / `silence` | 问"这批内容是否需要机器人介入"；节点自带允许答案集合与兜底；失败收工并记 `judge_fallback` |
| `qq-action-select` | 确定性为主 | `wake` / `steer` / `silence` | 见下节 |

去重（来源平台 + 账号 + 消息 id 唯一约束）仍在入站层完成，不作为节点。

## 六、动作选择

**代码优先，模型兜底**：

1. 该会话 `session_links` 上若有**在跑任务 id**，用 `task.get_status` 核实；仍在运行 → 本批内容**并入该任务**（`steer`）。
2. 没有在跑任务 → 复用已核实过的会话或新建会话，**新建任务**（`wake`）。
3. 代码判断不了的情况（例如"这批究竟是补充还是新话题"）才交给模型判断。

方向与 `qq-correspondence` 相反是有意的：动作选择涉及我们自己的运行时状态，模型看不到也不该猜。

`steer` 把批次转录并入在跑任务；`wake` 新建任务。两者都以批次为单位提交，`submission_id` 为批次 id。

提交结果的处理沿用现有语义：拿到 `task_id` 即记录；传输失败或服务端内部错误记为 `submission_unknown`，**不自动重发**；明确的提交前业务错误记为失败。提交前失败退回待判断状态，等待补入重试。

## 七、配置

新增到 Argus `settings.json`（非机密）：`batch_quiet_seconds`（默认 5）、`batch_max_messages`（默认 20）、`batch_max_seconds`（默认 60）。沿用：`judge_timeout_seconds`、`judge_attempts`（默认 3）、`recovery_interval_seconds`、`queue_capacity`、`qq.*`（含 `bot_names`）。

## 八、测试与验证

- **分组**：静默关闭、上限关闭、立即关闭、机器人自身消息不延长批次、迟到消息并入未判断批次、已判断批次不回头、重启后按水位重新成批。
- **节点契约**：`continue` 不产生终态、终态短路、事实合并、同一材料只取一次、有界循环上限、失败收工并区分原因、运行记录内容。
- **动作选择**：有在跑任务 → `steer` 且 `submission_id` 为批次 id；无在跑任务 → `wake`；`task.get_status` 显示已结束 → 新建；提交失败/未知的处理与现有语义一致。
- **端到端**：签名合成事件 → 成批 → 一次判断 → 提交（使用假 Jev、假 Gateway、临时数据库）。
- 真实 SnowLuma/付费 Jev 冒烟另获确认后执行，不使用真实聊天内容做断言。

## 九、明确不做

- 并行分支调度、检查点与跨进程恢复、运行中人工介入、图 DSL 与配置化拓扑。
- 按话题自动拆批（分组目前是确定性规则；若将来需要"这批包含多个话题"的判断，再作为节点引入）。
- 记忆/知识库检索节点（等 `packages/` 的 SDK 落地后接入，届时它属于"材料依赖"那一类）。
- 内容判断与回复生成（属于 Icarus）。
- "只记录""稍后再看"等额外终态。

## 十、落地顺序

1. 批次与水位的数据模型、成批规则（即时/静默/上限）、恢复按水位重建。
2. 节点契约与最小执行器（依赖顺序、事实合并、短路、有界循环、运行记录）。
3. 第一批节点改写现有行为，端到端回归（含真实链路复测）。
4. 动作选择（代码优先 + 模型兜底）与 `steer`。
5. 材料类节点（记忆、知识），随 SDK 落地。

第 1、2 步是基础；第 3 步完成后现有能力应与今天等价或更好（成本下降、看漏减少）。

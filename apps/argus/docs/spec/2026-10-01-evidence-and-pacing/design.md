# Argus 证据层与触发节奏设计

> 状态：已实现并经隔离测试与独立审查修复；当前源码事实见 [arch.md](arch.md)。本文保留设计依据。
> 配套 [实施计划](plan.md)。本轮未做真实QQ或付费模型冒烟。
> 实现未提交、不操作实际用户数据、不重启服务。
> 实现基线见 [批次与决策图架构](../2026-09-30-judgement-graph/arch.md)。本文实施后再依据代码、测试更新架构文档。

## 1. 目标与边界

Argus 观察群聊或私聊，结合前后文与 Icarus 的当前工作，决定：现在回应、补充当前任务、暂时等待，还是不用回应。它自己不生成或发送 QQ 回复。

本次设计包含三部分：

1. **证据与判断分开**：证据负责取得事实，策略负责做决定。
2. **观察与启动之间允许等待**：等待中的消息仍有处理机会，不因为本次没有启动就永久结束。
3. **整理项目内的图执行能力**：节点、边、图、单次执行状态与运行器各司其职，方便阅读、测试和组合；不是建设跨应用框架。

不做说话风格、人格、回复分条及记忆库、知识库、人物库的实际接入。未来这些库可以提供新的证据，但现在不创建没有调用方的空实现。Icarus 的性格依托认知这一方向不变。

测试阶段不为旧试验数据增加兼容层，也不为整理目录保留旧导入转发壳。这不表示应用可以自行删库；若实现需要重建试验库，须明确操作范围并单独执行。

## 2. 已核实的现状与需要纠正的认识

以下依据当前代码与测试，不把猜测写成故障结论：

- 同一 Icarus 会话的普通提交进入输入队列，逐个执行。连续提交会形成多个待执行请求，**不等于同时执行多个 Agent 任务**。见 `plugins/user_input/plugin.py` 的队列 worker 及其测试。
- `session.get` 返回的 `active_task_ids` 包含尚未移除的任务通道，其中可能有排队任务；不能将每个 ID 都当作正在执行的任务。还应读取排队数量，并按明确的任务 ID 查询状态。
- 会话存在与任务正在运行是两回事。当前 `QQTaskRelationPolicy` 用“无活动任务”直接返回 `new_topic`，不能据此认定用户真的换了话题。
- Argus 已保存观察消息、批次、判断结果和部分执行记录，也会给模型提供前序消息。它不是完全没有历史；不足在于工作状态区分不完整、判断材料和等待语义不够明确。
- 单条消息形成一个批次并不说明成批失败。之前使用的批次数量还混有迁移记录，不能作为新调度失效的证据。
- 时间很近的两次提交可能是正常追问。截图及提交间隔不足以证明每次回应都不必要，也不能直接认定表情包或抱怨与机器人无关。
- 当前图记录的是部分安全结果摘要，不是完整输入、全部输出或全部选边。当前节点版本也不恒为 `1`。
- 图中的控制边与必需结果依赖具有不同语义。排序时同时考虑两者，并不意味着两者重复、可以直接合并。

本次要解决的是已明确的设计缺口，不提前断言截图问题只有一个根因。

收件成功与是否回应分开：正常聊天落库后返回空204，不因后续silence/wait返回错误。签名及账号核实通过的心跳、生命周期、通知和请求事件也返回空204，但不落库、不进入判断；不据此自动接受好友或群请求。真正格式错误的消息和未知事件类型仍422；认证失败仍401/403。

## 3. 代码职责和目录

沿用仓库命名规则：文件、目录和函数用 snake_case，类用 PascalCase；应用代码留在 `apps/argus`，测试镜像源目录。

```text
apps/argus/src/
  evidence/
    icarus_state.py             # 读取并区分会话、执行中和排队中的任务
    recent_activity.py          # 读取本会话近期判断与提交记录
    qq/
      qq_conversation.py       # 当前消息、前序消息、已观察到的自身消息
  strategy/
    base_policy.py
    qq/
      qq_batch_policy.py       # 根据消息、时间、证据计算何时判断
      qq_intervention_policy.py
      qq_jev_intervention_policy.py
      qq_task_relation_policy.py
      qq_action_policy.py
  decision_graph/
    node.py                    # 节点接口与节点绑定
    edge.py                    # 条件边定义
    graph.py                   # 图定义、校验和执行顺序
    state.py                   # 单次执行状态、节点记录、运行结果
    runner.py                  # 执行、分支、预算、超时、失败传播
  service/
    batch_scheduler.py         # 调用节奏策略，安排唤醒和批次执行
    qq_service.py              # 构图、保存决定、执行 submit/steer
  clients/                     # 网络协议与连接
  dao/                         # 查询、事务和持久化
  entity/                      # 已有公共事实和业务结果类型
  utils/
    qq_transcript.py            # 把消息转换成供人和模型阅读的文本
```

`decision_graph` 名称本身没有妨碍当前用途，本期保留，避免为了抽象而改名。拆文件是为了明确职责，不强制一类一文件，不新增注册中心或图编辑器。

`TaskStatusReader`、`ContextReader` 的能力从 `service/qq_materials.py` 迁出。与 QQ 无关的 Icarus 状态读取不冠以 QQ 名称。

`transcript` 就是“聊天记录转文本”。它不查询、不判断，放在 `utils/qq_transcript.py`，让证据、策略和 service 复用，消除对策略文件的反向引用。不将 DAO、网络客户端或图运行器塞进 utils。

### 证据边界

- 返回事实或有来源的检索结果，不返回“应该回应”之类业务结论。
- 网络故障不是“没有任务”；历史不完整不是“没有历史”。缺失、截断和错误应显式区分。
- 读取动作通过已有 client/DAO 完成，不提交任务、不修改会话、不安排定时器。
- 复用现有公开类型；确实缺少字段时再扩展，不建立包住所有信息的通用上下文大对象。
- 不为版本号另造证据基类。证据和策略都可以作为图节点，但不要求证据继承策略基类。

## 4. 图执行能力的整理

### 4.1 接口保持简单、显式

节点执行一个异步操作，接收明确输入，返回明确输出。策略继续使用 `BasePolicy`；读取证据也可以使用同样的调用形式，不必引入多层继承。

图包定义最小节点调用协议，绑定记录直接给出节点 ID、执行函数、输入映射、必需结果、汇合方式和超时。输入使用现有公共类型或少量具名参数，不传任意可写的全局状态字典；多个参数采用明确的名称，避免靠元组位置猜含义。输入映射调用普通函数，不新增专用表达式语言。

边使用一个简单的数据定义，表示来源、目标和条件。没有不同边实现的真实需求，不另造抽象边基类。

### 4.2 两类依赖保留，但说明清楚

- **控制边**：前一个节点的结果是否允许走到下一个节点。
- **必需结果**：执行这个节点必须已经取得哪些节点的成功输出，即使另一条控制路径到达了它，也不能缺少这些材料。

两者都影响执行顺序。保留现有分支与汇合语义，以已有测试保护，不能为了减少接线项而悄悄改变行为。

图构造时校验节点 ID、边、依赖、入口、出口、可达性和无环约束，预先算好执行顺序。普通 Python 输入映射不能被完全静态证明正确；类型标注和组合测试负责检查，不承诺“编译后绝不会接错参数”。

### 4.3 单次执行状态明确归属

每次运行创建独立状态，保存节点状态、节点输出、选中的边、执行预算与节点记录。输入映射只能读取已产生的结果，不能修改其他节点的输出。

运行状态与业务结论分开：

- 节点执行状态：成功、失败、跳过、阻塞。
- 业务结论：需要回应、不需要回应、暂时等待等。
- 图失败不能被当作“正常决定不说话”。

运行器不导入 `RouteDecision` 等 QQ 业务类型，也不自行构造“沉默”决定。运行器返回执行状态与图出口值；`QQService` 校验业务输出，并将失败映射为明确的业务失败记录。安全摘要也由业务侧生成，不能把所有节点原始输出直接序列化入日志。

保留现有超时、总预算、取消传播和有界重复能力及测试。图内重复是一次运行里的有界计算，**不是跨时间等待对话**。跨时间的等待由调度器和持久化记录管理。

### 4.4 版本与诊断

不新增节点或图的人工递增版本制度，不将“有版本号”视为“执行状态完整”。清理节点版本的隐式反射读取；已有图版本字段如何保留或删除属于实现时的数据结构整理，不作为算法输入。试验比较记录代码提交号及实际参数即可。

每次运行保留安全的节点状态、选边、结果分类、耗时、错误类型及证据完整性摘要。状态查询端点展示这些摘要，不暴露原始聊天全文、模型完整输入、工具输出或密钥。不将开放整个原始输出对象视为“一行改动”。

## 5. 判断需要哪些证据

按 `(platform, account_id, subject)` 隔离；Icarus 历史还须核对 workspace 与 session 身份。

### 5.1 聊天证据

- 本批待处理消息及其明确消息 ID。
- 同会话前序消息，初始复用当前最近 10 条的限制，并标记截断。
- 已收到的机器人自身消息。它们提供上下文，不单独触发回应。
- 新到达但尚未归属本批的消息可作为背景，必须和本批待处理消息明确分开。

聊天是否延续不能只依据同一个群号，也不能只依据任务是否仍在运行。

### 5.2 工作证据

区分会话存在、加载中、当前任务执行中、任务排队、刚完成和状态未知。查询当前任务状态和相应历史，提供“当前收到的请求、已完成的步骤、可确认的进度”，而不是只给任务编号。

不从 `active_task_ids[0]` 猜正在执行的任务；使用明确任务状态核实。若无法确定唯一可追加目标，不盲目追加或另开任务。查询失败按失败处理，查询成功但仍有歧义可以暂时等待重新核实。

读取历史有条数和大小限制，记录是否完整。状态变化有竞态，执行副作用前仍须重验。

现有 RPC 的限制必须保留：`accepted` 表示已接收，不保证已执行；`queue_position` 不是持续更新的排队位置；`task_status_unavailable` 可能来自缓存缺失，不能当作任务完成。执行中只能读取已经落库的完整消息和工具开始/结束记录，不能获取尚未完成的文本流或工具结果。`user.message` 可能是展示文本，不保证等于执行提示词；Argus 自己的请求优先按 task ID 关联已提交参数。

会话历史读取在 Gateway 内可能执行历史恢复，因此“证据只读”指 Argus 不主动发出业务写操作，不承诺远端查询实现完全没有内部副作用。历史读取后再次取得会话状态，发现状态不一致时等待重新核实。上下文缺失应标明；若缺失的是识别追加目标所必需的材料，不盲目追加。

### 5.3 近期活动证据

记录正常介入判断完成时间、最近成功提交或追加的时间、连续正常“不需要回应”次数，以及统计窗口内的成功提交数量。

必须区分：

- 请求被 Icarus 接收；
- Icarus 任务完成；
- QQ 中实际观察到机器人发言。

三者不能互相冒充。没有 QQ 发送证据时，只说“此前已交给 Icarus 处理”，不声称“刚才已经回复过”。

## 6. 调度：短等待与退避分开

### 6.1 不主动找话，但保留正常回应

- 没有待处理的人类消息，也没有先前明确暂缓的请求：不因定时器到点而调用模型或启动 Icarus。
- 有未处理消息：即使之后群里安静了，仍可以到点判断，这是回应已有消息，不是主动找话。
- 没人点名的普通消息始终有判断入口；未来认知证据也从这条路参与判断。

### 6.2 先短暂等连续消息发完

普通群消息先给一个 1 秒的合并窗口，取值参考 MaiBot。这个短窗口可由新的人类消息更新，但不得让持续来消息无限阻止判断。

初始保留 20 条的单批大小限制和 60 秒的持续收集上限。60 秒限制的是连续新消息造成的收集推迟，**不能绕过仍在生效的退避期限**。达到存储/读取上限也不意味着消息全部必须提交给 Icarus。

### 6.3 两种退让，不把它们相乘

采用容易解释和测试的起点方案：

1. 连续两次正常判断“不需要回应”后，等待 15 秒再评估普通新消息；之后连续不需要则 30、60、120 秒增长，最多 300 秒。正常确认需要介入时结束这一连续计数。
2. 最近 300 秒成功提交了新请求，则普通消息增加 `15 秒 × 提交次数` 的最短判断间隔，最多 300 秒；提交一次即为 15 秒。追加到同一任务不当作新启动计数。
3. 两项同时存在时取较晚的允许判断时间，**不相乘**，避免轻易放大到几分钟。

第一项参考 MaiBot 的退避；第二项是本项目待验证的最简“近期启动过密则退让”规则，不声称来自 MaiBot，也不代表最优参数。

期限分别锚定正常判断完成时间、成功提交回执时间。不是每次扫描都从“现在”重新计时；普通新消息也不延长已经算出的退避期限。期限内的新消息会等待，因此不能声称“退避绝不增加响应延迟”。

一次普通判断的最早时机同时满足短收集窗口和退避期限。无历史时只应用短收集窗口；期限已过但无待处理消息时，什么也不做。

### 6.4 插队

- 人类私聊、明确 @、命中配置称呼：立即进入判断，并清除连续不回应的退避依据。清零需可恢复，不能只改内存。
- 待处理的人类消息达到 6 条：绕过时间等待；机器人自身消息不计入。每次仍受单批大小限制。
- 插队只表示更快判断，**不表示一定回应或一定追加当前任务**。
- 点名清零不删除实际提交历史；后续普通消息仍可受近期启动密度影响。

调度器执行计时和唤醒；节奏策略接收消息、证据、时钟和参数并计算结果。策略不创建后台任务。

## 7. 决策：先问需不需要，再问现在怎么处理

整个流程不以“新话题/旧话题”直接决定是否新建任务。

| 当前判断 | 处理 |
|---|---|
| 这些内容不需要回应 | 正常结束，记录原因 |
| 需要回应，确认没有执行中或排队任务 | 沿用现有会话提交；无会话时按既有规则创建 |
| 需要回应，无排队任务，有唯一已核实的执行中任务，而且适合现在补充 | 追加给该任务 |
| 需要回应，但暂不适合插入，或者仍有排队工作 | 保留待处理，等待后重判，不立即再排一个新任务 |
| 取证或判断失败 | 记录失败，不伪装成正常沉默 |
| 提交结果不明 | 保持现有未知态阻塞，不自动重发 |

“不需要回应”“暂时等待”“现在追加”是不同结果。普通情况下继续代码优先；需要理解语境、当前工作或近期处理结果时才使用模型。最近处理过的消息不能仅因私聊或 @ 就绕过所有上下文判断。

模型应知道本批哪些内容还未处理、之前哪些内容已交付、目前任务在做什么，并区分内容是补充、纠正、追问还是无需继续回应。不能仅因没有活动任务就断言“新话题”，也不能因为同一会话就认定所有内容都应追加。

无任务时可以省略“追加到哪个任务”的模型问题，**不能省略“是否还需要回应”的判断**。

需要提交时，只发送本次未处理内容及必要的延续说明。不重复拼接整个历史提示词；此前结果已有可靠证据时才加防重复提醒。

## 8. 等待、持久化和恢复

### 8.1 暂缓不是处理完毕

新增业务结果 `wait`（暂缓）和对应批次状态 `waiting`，与最终不回应分开。等待批次保存原因和下次可重判时间；未发生 submit/steer。

保持已有批次成员固定，不在等待期间向其追加成员。新消息仍正常落库，尚未归属的消息继续收集。一个会话优先处理最早未结束的批次，后续批次不得越过它产生外部动作。

重新判断等待批次时，可以读取新消息作背景，但明确这些消息不属于当前待执行载荷，不声称已处理它们。当前批次结束后，后续消息再结合最新结果判断，避免把背景内容重复当作新请求执行。只读背景不改变消息归属。

### 8.2 何时重新判断

- 新消息到达，尤其是点名或纠正；
- 定期检查确认当前任务已经结束，或排队工作已发生变化；
- 已保存的等待期限到期。

先做便宜的状态检查，等待中的会话默认每 5 秒检查一次，新人类消息到达可提前检查；同一等待原因下，状态与消息均未改变时，不重复调用模型，而是推进下一次检查期限。复用现有调度检查机制，不新增常驻模型循环或网络订阅协议。

本期 `wait` 只用于存在运行中、排队中、加载中或无法确认可用目标的工作状态。不增加模型任意指定“空闲时再想一会儿”的能力，避免没有变化依据却无限等待。确认工作空闲后，重新判断本批是否仍需回应，然后提交或结束。

“状态变化”至少比较任务 ID 与状态、排队情况、观察消息顺序号及可用的会话历史进度序号；不能使用每次变化的查询时间戳，否则每次检查都会误认为有新进展。判断使用的证据水位应在读取时固定并随结果保存，不在模型返回后读取最新水位冒充已看过的消息。等待批次即使没有变化也只做便宜检查，不让后续批次越过它发送；后到的点名或纠正会先唤醒最早等待批次重新判定。

任务完成后重新判断，不无条件执行旧决定：原问题可能已经被回答，也可能被用户取消。判断结果可以是继续等待、无需回应或现在处理。

### 8.3 最小持久化要求

不新增专用状态表；在批次记录中补齐必要的时间和等待信息，并通过观察记录恢复强信号清零依据。具体字段在实施计划中与现有类型对齐，至少必须表达：

- 正常介入判断完成时间；
- 成功交付时间及方法；
- 等待原因、下次检查时间、上次重判所依据的消息和任务状态摘要。

不得用 `updated_at` 代替所有时间，因为状态转换会修改它。统计排除当前未完成批次、纯自消息批次、等待结果和错误结果；只计入正常介入判断的“不需要”。失败不构成正常沉默，也不解除结果不明的阻塞。

强信号重置记录依据为最近的人类私聊、明确 @ 或称呼命中的观察顺序号。连续沉默计数只计算重置之后的有效结果；同一条强信号不因反复扫描而反复重置。新建观察字段 `is_strong_signal` 在收件时按当时配置计算并与观察同事务保存，作为稳定的重置依据；不在每次扫描时按可能已变化的名字配置重新解释旧消息。每次正常判断记录其覆盖到的观察顺序号，以排除在强信号之前取得的旧判断。

等待批次重启后仍是待处理，复用同一批次身份；不能变成“已沉默结束”。已经交付的批次不重放。图执行记录按运行区分，重判不能把前一次等待原因覆盖得无法追溯。增加按会话、顺序或统计时间查询所需的索引，不声称一个索引能覆盖所有访问模式。

### 8.4 执行前复核

图完成后，service 在每会话串行执行边界内重新核实任务状态。原定追加的任务已经完成时，应结合最新结果重新判断是否仍需提交，不直接自动改为提交。

原定提交时若出现运行中或排队任务，转为等待或重走追加判断。仅在 Argus 内加锁不能防止其他客户端同时提交；本期保证 Argus 不在已知忙碌时继续堆积请求，不承诺跨客户端的原子独占。Agent 现有输入队列继续保证正常提交串行执行。

连接失败或回执不明仍按既有 `submission_unknown` 处理，不借重判绕过幂等和发送边界。

## 9. 截图场景的目标处理方式

以“缺美术素材 → 你真能产出吗 → 表情 → 对策略的反馈”为例，不预定模型必须如何理解每一句：

1. 第一条连同前文进入判断；若确实适合参与，启动一次。
2. 后续追问与表情先按当前节奏收集。取证明确第一轮已完成、执行中还是排队中，并展示可确认的处理结果。
3. 若第一轮仍在执行，判断追问是否应补充进去；不适合打断但仍需处理时，进入等待。
4. 若第一轮已完成，追问有新内容就允许再次启动，不因“刚回复过”硬性禁止；没有新需要则不启动。
5. 对策略的反馈也要结合上下文判断，不能预先认定为无关。若是取消、纠正或制止信号，应影响待处理请求的重判，而不是机械排一篇新回答。
6. 群里随后安静，但还有明确等待的请求，任务结束后仍重新检查；若所有请求均已处理，不再自行找话。

目标是减少重复处理，保留正常追问，避免请求被遗忘；不是将一段时间内的提交数量硬压成一次。

## 10. 如何验证正确有效

### 10.1 确定性测试

使用假时钟、临时数据库、假 Gateway 和假 Jev，不读取真实凭据或发送 QQ 消息。

- 节奏：1 秒收集、连续第二次不回应后 15 秒退避、指数增长与 300 秒封顶；启动密度与退避取较晚期限；普通新消息不推迟退避；旧 60 秒收集上限不绕过退避。
- 插队：私聊、@、称呼与 6 条人类消息；自身消息不增加积压、不产生自唤醒；重启后清零依据正确。
- 等待：任务进行中，不适合追加的有效请求保留；任务结束且用户未再发消息也会重判；已解决则结束、仍需处理则执行一次。
- 路由：区分执行中、排队、完成、加载中、未知与查询失败；不把多个 active ID 当并发执行；不猜追加目标。
- 竞态：判断期间任务完成、另一个客户端提交、追加被拒绝；不自动变成第二份重复提交；未知结果不重发。
- 消息归属：批次成员固定，后到背景不算已处理，同一来源重投不产生第二条记录。
- 图：保留分支、必需结果、汇合、循环、预算、超时与取消测试；证据节点和策略节点都能独立组合；两次运行状态互不污染；运行器不依赖 QQ 业务结果。
- 可观测性：区分等待、正常不回应、图失败和发送不明；保留每轮安全摘要，日志不包含秘密或整段聊天全文。

### 10.2 场景评价

建立少量可读对话样例，给出每一步允许的动作，而非只写最终提交次数：连续补充、正常追问、纠正上一请求、换话题、纯表情、旁人闲聊、用户制止，以及等待后已被他人解决。

分别看：

- 是否重复处理已经完成的请求；
- 是否漏掉应该回应的新问题；
- 是否在不合适的时候打断当前任务；
- 普通消息等待是否过长；
- 模型调用量与失败量是否合理。

不以“70 秒内再次启动”定义重复，不以“无人接话”判定启动错误，不要求“80 秒最多提交一次”。

旧观察消息仍可用作样例，旧策略结论不能充当标准答案。可靠回放还需要当时的任务状态、判断输入、参数及模型答案；不能声称现有历史库已完整保存这些信息。新旧方案比较应使用固定证据和假模型答案检查流程，再用人工复核与小规模真实测试检查判断质量。

验证顺序：最小受影响测试、`make test-argus`、编译和 diff 检查。如实现涉及 Agent/Gateway 合约，先单独讨论，再增加对应应用测试。真实端到端测试另行确认群、账号、费用和外部发送范围。

## 11. 实施与文档纪律

本设计经过用户评审后，再编写实施计划。整理图能力、建立证据包、加入调度与等待、验证场景应分成可独立验证的步骤；不把未经实现的能力写进 arch.md。

保留用户已有配置改动，不启动真实服务，不使用备份聊天全文生成外部分享页面，不擅自迁移或清除其他应用数据。未经明确要求不创建分支、不提交、不推送。

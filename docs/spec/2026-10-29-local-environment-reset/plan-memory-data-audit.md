## 必须保留的解释边界

既有 [portable integration 计划](plan-portable-integration.md) 明确记录“old local databases have already been cleared”。因此当前缺口可能与已授权环境重置有关，也可能涉及未迁移的数据或其他操作；仅凭历史 ADD 仍在，不能判定迁移失败、未授权删除或永久丢失。

旧 history.db 包含过删除事件；它是审计材料，不是应当全部重新写回的目标清单。不能将所有历史 ADD、用户会话文本或截断工具预览自动重新导入，以免恢复用户曾要求删除或停用的内容。

## 2026-11-06 核对结论

### 是否由用户切换导致

当前 Agent 配置为 `user_id=removel`、`agent_id=icarus`。现存两条记录均匹配这两个身份，一条 `run_id=global`，一条 `run_id=workspace:83bba66c7a926a4f`。直接管理列表与网页代理均得到这两条；当前没有切错用户或连接到不同数据库的证据。

Agent 自动召回限制为当前 user、agent 及 global/当前 workspace。切换身份或工作区会改变召回范围；管理页面默认列出所有用户/范围，只有显式筛选时缩小结果。因此用户切换可以导致“召回不到”，但不能解释目前默认管理页面与主表一致、只有两条的观测。页面筛选继续保留，新增列表刷新不会偷偷清空筛选。

### 新写入与历史缺口的证据边界

历史 Session 中存在 2026-10-24 声称保存 1、4、2 条的工具记录，当前主表缺少其中对应历史 ADD ID；它们本身不足以证明当时实际落库。另一个旧预览目录未找到可访问的备份文件，旧集群权限仍不足，未改权限或启动旧库。现有环境重置计划明确记载旧本地数据库已清理，无法从现有材料重建完整搬迁时间线。

本轮在隔离测试中复现 Mem0 的确定性缺陷：推断写入的批量和逐条 insert 都失败时，旧代码仍返回成功 ID 并写 ADD 历史。同步、异步已修复并测试；这说明成功 ID/ADD 历史在旧实现下也不是充分落库证据，**不能据此确定历史 7 个 ID 是该缺陷造成**。

当前可确认的代码问题是持久化错误被吞、Agent 空/畸形响应反馈不严谨、页面缺少外部写入刷新，以及管理分页的 1000 条上限。后三者各有独立回归，容量问题未在当前两条数据触发。修复入口见统一实施计划。
